# ファイル一覧の保持

文書ルート(`ORENO_ROOT`)以下のファイルの一覧を、サーバーのメモリに保持する。ファイル一覧を必要とする機能(今はリンク設定モーダルの候補)は、毎回ディスクを走査せず、この一覧を使う。実装は `src/lib/fileIndex.ts` に集約している。

## 基本方針

- 文書セットはDockerのバインドマウントで置かれることが多く、その環境ではファイルの変更を監視(fs.watchなど)してもイベントが届かないことがある。そのため監視は使わず、定期的なスキャンで更新する
- 一覧を必要とするときは、その時点で保持している一覧をそのまま使う。利用のたびに再スキャンして待たせることはしない
- 一覧はサーバープロセスごとに別々に持つ。複数プロセスでの運用は想定していない

## 一覧に含めるもの

- 文書ルート以下のファイルすべて(Markdown以外も含む)。フォルダは含めず、ファイルのないフォルダは一覧に現れない
- 各ファイルは、文書ルートからの相対パス(`/` 区切り、拡張子付き。例: `docs/guide.md`)で持つ
- `.` から始まる名前のフォルダ・ファイル(`.oreno`、`.git` など)は含めない。フォルダは中も辿らない
- シンボリックリンクは無視する(辿らない。循環を避けるため)
- URLにできない名前(`*` を含むなど)のファイルは含めない。Markdownは拡張子 `.md` を除いた名前のページとして、それ以外はファイルとして、`docPath.ts` の `resolveDocPath` / `resolveFilePath` で検証する

## スキャン

- フォルダ単位で順に `readdir` して走査する(並列にしない。一斉に読むと、特にバインドマウントでI/Oが集中するため)。非同期の `readdir` を使い、イベントループを塞がない
- 権限エラーなどで読めないフォルダは、飛ばして続ける。文書ルートが存在しない場合も、一覧が空になるだけでエラーにしない
- スキャンが完了すると、一覧をスキャン結果で丸ごと置き換える
- 最初のスキャンはサーバー起動直後に始める。以降は10分周期で、前回のスキャンが完了してから次のタイマーをセットする(スキャンが重ならないようにするため)
- すでにスキャン中のときに更新を依頼されても、何もしない(次のスキャンを予約することも、待たせることもしない)。依頼は `requestFileScan()`
- スキャンの失敗は、ログに出すだけにして、プロセスは落とさない
- `ORENO_ROOT` が未設定の場合の扱いは、この仕組みでは考慮しない(別途、起動時にエラーで終了させる予定)

## アプリ操作の即時反映

ページの保存(作成を含む)・移動・削除は、Server Action(`src/app/actions.ts`)から、次の関数で一覧にすぐ反映する。

- `registerFile(slug)`: 保存、移動先
- `unregisterFile(slug)`: 削除、移動元

- 対象はページ(`.md`)だけ。画像など他のファイルは、アプリから作成・削除する機能がないので、スキャンだけで更新される
- スキャン中に呼ばれた変更は、すぐには反映せず、保留して順番に覚えておく。スキャンの完了時に、スキャン結果に対して順に適用する。そうしないと、スキャンが変更の前に読んだ古い結果で、変更が上書きされて消えてしまう
- 保存はページの更新のたびに呼ばれるので、すでに一覧にあるときは何も変わらない(登録は重複しない)
- `.` から始まる名前のページは登録しない

## 起動の仕組み

- スキャンの開始は `src/instrumentation.ts` の `register()` から `startFileScan()` を呼ぶ。`register()` はサーバー起動時に一度だけ呼ばれ、その完了までサーバーが待たされるため、スキャンの完了は待たない
- Edgeランタイムでは `fs` が使えないので、`process.env.NEXT_RUNTIME === "nodejs"` のときだけ始める
- 一覧の状態は `globalThis` に持つ。Next.jsは起動時の処理とServer Actionを別々にバンドルするため、モジュール変数だと別々の状態になってしまう。開発中のHMRでモジュールが作り直されても状態が残る効果もある
- `startFileScan()` は何度呼ばれても、始めるのは一度だけ

## 一覧の取り出し

- `getFileIndex()` が、`ready`(最初のスキャンが完了したか)、`scanning`(スキャン中か)、`files`(一覧)を返す
- `scanning` が true のとき、`files` はスキャン前の一覧
- `ready` が false のとき、`files` は空。利用する側は、一覧がまだないことを利用者に示して、しばらくして取り直す
- クライアントには、Server Action `getLinkCandidates(refresh)` で渡す。`refresh` が true のときは、更新(スキャン)の依頼も同時に行う。結果の受け取りは、サーバーからの通知(WebSocketやSSE)ではなく、クライアントのポーリング(1秒ごとの再取得)で行う。通知が必要なのはモーダルを開いている短い間だけで、実装の規模に見合わないため
- リンク設定モーダルでの使い方(候補の表示条件や並び順)は、`oreno-editor-ui` のSKILLの「リンクの設定」を参照

## 他の機能との関係

- ドットで始まる名前を「処理対象外」とする方針は、この一覧では実装済み。既存の他の機能(閲覧履歴の記録、Markdown文書の保存・表示など)は `.oreno` だけを除外しており、方針と揃っていない。揃える修正は別途行う予定
- ファイル一覧を必要とする新しい機能は、ディスクを走査し直さず、`getFileIndex()` を使うこと
